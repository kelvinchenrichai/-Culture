# Phase 7 — 小節日內容擴充 & 插畫分享卡

## 這輪要解決的問題

使用者原話（節錄）：「除了剪頭髮那天還有適合什麼事情，然後哪一個神明生日誕辰可以去拜拜，或是
特別什麼節日等等的，我要的就是把那些可能平時不太會在意的、不會去拜拜的都提醒出來，又或是很多
族群會去天赦日，或是拜財神、虎爺等等，或是甚麼菩薩得道日等等這類的小細節、小日子，也都要提供
給這些用戶去分享」。另外也希望分享卡的圖片能帶一點「神明感」或山水意境，做成「高級版、有用版、
可以點擊的長輩圖」。

## 這輪做了什麼

### 1. 真實的 156 筆神明/節日事件，其實早就在資料裡，只是被丟掉

`public/data/calendar/2026/*.json`（LunarData，MIT 授權，已在 `docs/data-sources.md` 列冊）
每一天原本就帶完整的 `deityInfo` 陣列（名稱、稱號、農曆日期、描述、供奉場所、常見祈求、備註），
2026 全年共 156 筆真實事件。過去 `lunarDataProvider.ts` 只取出事件名稱字串塞進
`deityBirthdays: string[]`，其餘欄位在轉成 `CalendarDay`這一步就整批被丟掉，`RealDeitiesView`
也只顯示「今天」對到 6 位精選神明才有的名稱。

修法：
- `src/lib/calendar/types.ts` 新增 `DeityDayEvent` 型別，`CalendarDay` 新增
  `deityDayEvents?` / `goodDayGods?` / `badDayGods?`（皆為附加欄位，不影響既有型別使用者）。
- `src/lib/calendar/lunarDataProvider.ts` 新增 `toDeityDayEvents()`，逐欄位原樣對應
  （沒有的欄位就是 `undefined`，不生成、不腦補任何內容），並把 `goodGods`/`badGods` 一併帶出。
- `components/RealDeitiesView.tsx` 全面重寫「今天拜什麼」區塊：改成列出 `deityDayEvents`
  裡的每一筆真實事件（可展開看完整描述/常見祈求/供奉場所，附「資料來源：LunarData」），
  不再只靠對到精選 6 位神明才顯示。

### 2. 天赦日：一年只有 5–7 天的特殊吉日，過去完全沒有算

`goodGods` 欄位裡是否包含「天赦」二字，LunarData 自己已經算好了；本站只是把它讀出來，不是
重新實作曆法規則。新增 `src/lib/calendar/specialDays.ts`：
- `isTianSheDay(day)`：讀 `goodDayGods` 有沒有「天赦」。
- `TIAN_SHE_DAY_EXPLANATION`：通書裡對天赦日的傳統說法（百無禁忌、適合化解糾紛/祈福還願），
  不是本站自創的判定或誇大宣稱。
- 今天若是天赦日，`RealDeitiesView` 最上方會有一個獨立的天赦日提示卡，附自己的分享按鈕。

留意：天赦日當天，LunarData 的 `deityInfo` 自己也會另外放一筆同名「天赦日」事件（欄位比
`TIAN_SHE_DAY_EXPLANATION` 更詳細）。為了不要讓使用者在同一頁看到兩次「天赦日」，事件列表
跟「近期特殊日子」清單都會把這筆同名事件濾掉，只在專屬的天赦日提示卡顯示一次
（`tests/specialDays.test.ts` 有測這個去重邏輯）。

### 3. 「近期特殊日子」：主動攤開接下來 14 天，不用使用者自己每天點進來查

使用者原話：「我要的就是把那些可能平時不太會在意的、不會去拜拜的都提醒出來」——不是被動等
使用者今天點進來看今天，而是主動告訴他接下來兩週有什麼。新增 `findUpcomingSpecialDays()`，
掃描未來 N 天、只回傳「有事件或是天赦日」的日子（避免列表被一堆空日子灌水），
`RealDeitiesView` 用它顯示未來 14 天內的節日/天赦日，每一筆都有獨立分享按鈕。

### 4. 分享卡插畫：手繪 SVG 向量圖案，不是照片

使用者希望分享卡能帶「神明圖片」或「山水」之類的裝飾感。這輪明確詢問過使用者要走哪個方向，
使用者選擇「自製風格化插畫」，原因（`src/lib/share/illustrations.ts` 開頭有完整說明）：真實
宮廟/神像照片有版權跟宗教尊重上的疑慮（跟本站從 Phase 5 開始就刻意避開「授權不明的網路圖片」
一致），公版古畫需要額外查證授權，純向量插畫兩者都不用擔心，配色也能跟卡片主題完全搭配。

新增四種手繪 SVG 剪影，依卡片風格自動搭配：山水（今日宜忌卡/生活一句卡）、蓮花（神明祝壽卡，
刻意用蓮花這種不特定單一宗教/宮廟的通用祥瑞符號，不是某間特定廟的神像）、祥雲（生活決策卡）、
廟宇屋簷剪影（保留給未來需要強調「這是關於某間廟」但仍抽象化的內容）。插畫用 `opacity: 0.12–
0.16` 疊在卡片背景，不會蓋掉文字，下載出來的 PNG 圖卡跟畫面上的即時預覽用同一個
`renderMotif()` 函式，兩邊保證長得一樣。

## 這輪順手抓到的既有 bug（驗證這批新功能時發現的，不是新功能本身的問題）

### A. 分享卡 modal 的「樣式分頁」不會照呼叫端指定的樣式打開，永遠停在上次手動選過的分頁

`ShareCardModal` 從頭到尾只掛載一次（`isOpen` 只是控制要不要 `return null`，不是控制
mount/unmount），畫面上「樣式分頁」（今日宜忌卡/生活一句卡/神明祝壽卡/生活決策卡）用
`useState(initialData?.style || 'cultural-minimal')` 設初始值——這個初始值只有**第一次**
render 會讀到 `initialData`，而 App 第一次開啟分享卡時 `initialData` 通常還是 `undefined`。
結果就是：不管之後從神明頁點「分享這位神明」（帶 `style: 'deity-blessing'`）、還是從決策結果頁
點「分享這個結果」（帶 `style: 'decision-ticket'`），分頁永遠停在使用者上一次手動點過的樣式，
呼叫端指定的 `style` 完全被忽略——這輪新增神明事件分享按鈕時，實際點開才發現不管傳什麼
`style` 進去，畫面一直顯示「今日宜忌卡」。

修法：加一個 `useEffect`，在 `isOpen` 為真、且 `initialData` 變動時重新同步 `activeStyle`，
而不是只在 `useState` 初始化時讀一次。用 Playwright 實際點開多個入口的分享按鈕，確認每個
入口現在都會正確打開對應的樣式分頁。

### B. 下載圖卡：標題沒有斷行，長標題會直接切出卡片外

`createGenericShareCardSvg` 的標題原本是單一個沒有寬度限制的 `<text>` 節點。「生活決策卡」
樣式的標題實際上是 `initialData.primaryText.split('！')[0]`——這是為了「適合！大吉」這種短
判詞設計的，但只要呼叫端傳進來的 `primaryText` 不含全形驚嘆號（例如把一整段神明介紹文字當
`primaryText`），`split` 結果就是整段長文字，會直接從卡片右邊界一路溢出到看不見，實際下載
下來的 PNG 標題只剩半句、看起來像是壞掉的圖檔。這是這輪加神明事件分享、用 Playwright 真的
下載一張 PNG 打開檢查才抓到的（不是靠讀程式碼猜的）。

修法：標題比照 `lines`/`quote` 用同一套「優先在標點/空白斷行」的 `wrapText`，並限制最多 3 行、
超過就在最後一行結尾補「…」，避免極端長標題把整張卡撐爆。加了兩個新測試守住這個行為
（一般長標題會斷成多行、超長標題會截斷加刪節號），並把下載出來的 PNG 重新截圖比對修好。

## 這輪沒做的事（刻意，不是漏掉）

1. 生活決策分類目前仍是原本的 6 種（剪頭髮/拜拜/搬家/開工/結婚/出門）。使用者有提到「今天
   適合搬家等等的還有更多的」，資料裡的 `auspicious`/`inauspicious` 陣列其實已經有更多細項
   可以擴充，但要擴充成使用者好懂的分類名稱、對應到哪些農民曆宜忌詞，需要另外一輪梳理，
   這輪先把「小節日」這塊做完。
2. 「長輩底層邏輯＋年輕化視覺」的整體設計統一，跟 Phase 6 一樣，仍是刻意保留給使用者先看過
   方向再決定的獨立任務。

## 驗證方式

`pnpm test`（150 個測試全過，含這輪新增的 `specialDays.test.ts`、`calendarProvider.test.ts`
補充測試、`shareCard.test.ts` 的標題斷行迴歸測試）、`pnpm run build`、`pnpm run lint`
（`tsc --noEmit` 通過）。另外用 Playwright 對本機 production build 實際操作：把系統時間
模擬成真實的天赦日（2026-03-05）確認天赦日提示卡正確顯示且不重複、模擬一般日期
（2026-01-05，阿彌陀佛聖誕）確認事件卡可以展開看到完整描述、近期特殊日子清單正確列出未來
14 天內的節日、點開多個分享入口確認樣式分頁正確對應、下載 PNG 圖卡並用 Read 工具實際打開
檢查標題斷行結果。
