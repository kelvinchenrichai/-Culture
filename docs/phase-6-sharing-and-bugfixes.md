# Phase 6 — Bug Fixes & LINE Sharing

這份文件是這一輪的總覽：使用者上線體驗後回報「資料跟內文有一些 bug」，並希望「容易在 LINE
裡面分享推廣」。這輪先做全站走一遍找真實 bug，再針對分享功能補上原本缺的東西。長輩體驗跟
年輕化視覺風格統一（原始需求的第三部分）規模較大、屬於視覺設計決策，**這輪刻意不做**，留在
下一輪先出設計方向讓使用者確認，避免沒對齊方向就大改一輪視覺。

最後更新：2026-09-02。

## 這輪怎麼找 bug

沒有用猜的，也沒有直接問使用者要截圖——而是把 `main` 的正式版本本機建置、跑起來，用
Playwright 實際點過每一個主要頁面（今天拜什麼、生活決策、找好日子、附近寺廟、拜拜教學、
分享卡），逐一讀取畫面上真正顯示的文字，比對程式碼找出根因。

## 找到的真實 bug

### 1. 內部草稿用語外流到正式畫面

`RealDeitiesView.tsx` 跟 `RealDeityDetail.tsx` 裡，這幾處文字不是說給開發者看的 dev-only
標記，是**所有使用者都看得到**的正式文案：

- 「神明資料（**內容種子**）」——這是內部工程用語（content seed），不是使用者看得懂的說法。
- 「常見供品（**內容種子，正式上線前仍需編輯驗證**）」——同上，而且聽起來像網站還沒做完。
- 「此資料目前為 **sample**」——直接把程式內部的英文狀態代碼（enum）印進中文句子裡。

修法：改成白話說法（「認識更多神明」、拿掉欄位標籤裡的內部備註、`dataStatus` 用一個對照表
轉成「初步整理，尚未逐項查證」這類人看得懂的句子），邏輯跟資料完全沒動，只是不再讓使用者
看到工程備忘錄。

### 2. 神明資料上下矛盾：同一個日期，一個看起來不可信、一個已查證

神明詳細頁上半部顯示未附來源、標「sample」的舊版單一日期猜測；下半部「逐欄位資料來源」又
重新顯示一次同一欄位，這次有正式來源標「已核實」（例如媽祖前一輪查證到的聖誕/飛昇兩個日期）。
兩份資料同時存在、互相矛盾，使用者看了反而更不確定該信哪一個。

修法：有查證過的 `profile.dates` 時，上半部不再重複顯示未附來源的舊猜測，直接讓查證過的版本
當唯一顯示的版本。

### 3.「分享這個好日子給親友」分享的其實是「今天」，不是使用者選的那一天

`FindDaysView` 點某個未來日期（例如 9/7 剪頭髮吉日）的分享按鈕時，有把該日期的資料
（`initialData`）傳給 `ShareCardModal`，但 modal 的「今日宜忌卡」畫面**完全沒有用到**
`initialData`，只會顯示 `today`（今天）的宜忌——分享出去的圖卡資訊是錯的，講的是今天，不是
使用者要分享的那一天。

修法：`ShareCardModal` 改成有 `initialData` 就一定顯示它，沒有才退回顯示今天（例如首頁一般
的「分享今日」情境）。

### 4. 分享功能完全沒有「圖片」可以下載——長輩想轉傳的東西其實做不出來

畫面上的「精美卡片」只是網頁上即時預覽的一個 `<div>`，沒有任何存成圖片/下載的按鈕。更意外的
是：專案裡其實已經寫好一個會產生 1080×1080 SVG 圖卡的 `ShareCardService.createSvg()`，
也有單元測試，但從頭到尾沒有被任何畫面 import、完全是死代碼。使用者這輪明確要的「適合長輩
轉傳的圖卡」，在技術上其實還做不到，只能傳純文字。

修法：新增 `createGenericShareCardSvg()`（1080×1350 直式，適合手機），把分享卡目前顯示的
內容轉成 SVG →（用 canvas）轉成 PNG → 觸發下載，新增「下載圖卡」按鈕。已用 Playwright 實際
點過下載按鈕、存下真的 PNG 檔案確認可用（105KB，內容正確、斷行正常）。

### 5. LINE 分享文字沒有附網站連結

`handleShareLine` 只送出文字內容，沒有帶回網站的網址——朋友收到訊息後沒辦法點回來，等於少了
「分享推廣」最後一步的轉換路徑。

修法：統一抽出 `src/lib/share/lineShare.ts`，預設一律附上 `https://culture-as5.pages.dev`，
之後要換網域只需要改一個地方。

### 6. 分享功能只有兩個入口，神明頁/決策結果頁/寺廟頁完全沒有分享按鈕

整個 App 只有「首頁」跟「找好日子」呼叫得到分享 modal。神明詳細頁、生活決策速查結果頁
（剪頭髮/搬家/開工等）、附近寺廟頁完全沒有分享功能，即使程式裡曾經有給舊版原型元件
（`DeityDetailView.tsx`、`DecisionView.tsx`）寫過類似的分享呼叫，但這兩個舊元件其實
**沒有被 `App.tsx` 引用、根本不會被使用者看到**（純粹的死代碼，不是這次改動的範圍）。

修法：`RealDeityDetail`、`RealDecisionView` 加上分享按鈕，接上既有的 `ShareCardModal`；
`RealTemplesView` 每一間廟加上一個輕量「分享給朋友」按鈕，直接用 LINE 深連結分享廟名/主祀/
地址/導航連結（不需要開完整卡片 modal，寺廟資訊本身就是重點）。

## 這輪沒做的事（刻意，不是漏掉）

1. **長輩底層邏輯 + 年輕化視覺的設計統一**（原始需求第三點）：這是整體視覺設計方向的決策，
   影響全站十幾個元件的配色、字級、版面邏輯，屬於主觀判斷，值得先出一版方向或幾個畫面的
   設計提案讓使用者確認喜不喜歡，再決定要不要全站套用，避免方向不對卻已經改了一輪。
2. 4 種分享卡樣式（今日宜忌卡/生活一句卡/神明祝壽卡/生活決策卡）目前共用同一種 SVG 版面
   （直式、單一欄位排版），沒有針對每種卡片風格各自客製版面。內容正確、可以下載分享，但
   視覺上還沒有 4 種明顯不同的「卡片感」，可以在設計統一那一輪一起處理。
3. 舊原型元件 `DeityDetailView.tsx`、`DecisionView.tsx` 是死代碼，這輪沒有刪除，只是確認過
   不影響正式畫面。之後可以考慮整批清掉降低維護負擔。

## 驗證方式

`pnpm test`（139 個測試全過，含這輪新增的 `lineShare.test.ts` 跟 `shareCard.test.ts` 補充
測試）、`pnpm run build`（bundle size 沒有異常增加）、`pnpm run lint`（`tsc --noEmit` 通過）、
另外用 Playwright 對本機 production build 實際操作驗證：神明頁文案不再外流內部用語、找好日子
分享卡確實顯示使用者選的那一天而不是今天、下載圖卡按鈕真的能產生內容正確的 PNG 檔案、三個
新增分享按鈕（神明/決策結果/寺廟）都確實出現在畫面上。

## 上線後使用者回報、本輪之後又修的 bug

### 7. 生活決策頁：不管點哪個分類，標題永遠停在第一次打開時的那個分類

使用者實際截圖回報：在「生活決策速查」頁面，不管點「拜拜」「搬家」「開工」哪個分類 chip，
畫面標題（例如「今天適合剪頭髮嗎？」）都不會換成對應分類的問句，一直停在最初打開頁面時的
分類，即使 chip 本身的選取樣式看起來有換。

追原因：`RealDecisionView` 原本用 `choices.find(item => item.id === selectedId) ?? choices[0]`
算出 `selected`，這是一個「prop 衍生的常數」，每次 render 都重算一次沒錯，但畫面上的標題其實
是照使用者輸入/點擊之後 `parseQuery` 解析出來的 `intent` 去找對應分類顯示，跟 `selected` 這個
常數各算各的、沒有互相同步。

修法：把 `selected` 改成 `useState`，並且在 `run()`（實際執行查詢、拿到 `parsed.intent` 之後）
裡面用「解析出來的 intent 對應到哪個分類」去 `setSelected(...)`，讓標題、chip 高亮、自由輸入
查詢三者都讀同一份真正反映「使用者最後查的是哪個分類」的 state，而不是各自猜測。

用 Playwright 對本機 build 依序點過全部 6 個分類 chip、逐一截圖比對標題確認全部正確換行，
另外也測了自由輸入查詢框（不點 chip、直接打字問「今天適合搬家嗎」）也會正確更新標題——這是
統一成同一份 state 之後順便修好的，原本這條路徑也有一樣的問題。
